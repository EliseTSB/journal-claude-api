Gateway API

The JJ-facing guide to the metered LLM gateway. Two ways in: run it through the opencode harness (three commands, no code), or talk to the raw OpenAI-compatible HTTP API directly. Distinct from the RTC/Journal-Claude API (api-docs.md) — this endpoint is a model, not Claude, and it is stateless HTTP rather than a WebRTC session. The base URL and API key are placeholders by design; the real values reach you from the operator. LIVE since 2026-07-09.

Start here: you do not have to build a client first

There are two ways in, and the easy one comes first. Most of this document is the raw wire — useful, and the thing you eventually want to understand. But you can be using the gateway in about three minutes without writing a line of it.

Use opencode as your harness. It is a terminal program that already speaks this API; you point it at your key and start working. In a Codespace terminal:

curl -fsSL https://opencode.ai/install | bash

Then put the opencode.json Elise sent you at the top level of the project, and run:

opencode

/model inside it lists the models you can actually reach. That command is the answer, not a list in this document — the roster changes when the models behind the gateway change, so a table here would go stale and /model never can.

Default to deepseek-v4-flash for basically everything unless you have a reason not to. Per Elise it is the dominant option right now for the price, and she is the one running the benchmarks.

Your opencode.json contains your API key. If it lands in a git repo, the key is public — anyone who finds it can spend your budget. Add it to .gitignore before you commit anything. This is not housekeeping; it is the first real lesson attached to this module, and it is why git comes before models.

Your budget (so nothing is a surprise): $2 per 5 hours · $5 per week · $10 per month. There is no request-rate limit. Spend it on anything you like — this is what it is for.

Overview

The Gateway API is an HTTP service that gives you metered access to a pool of open-weights language models. You send it a chat request; it routes the request to a model, runs it, meters your usage, and sends the answer back.

Key characteristics:

  • OpenAI Chat Completions compatible. Requests and responses use the standard OpenAI shape (POST /v1/chat/completions, messages: [...], choices: [...]). Anything you read in OpenAI/Groq/Together tutorials applies here, mostly unchanged.
  • Stateless. Every request stands alone. The server keeps no memory of past requests. Conversation context is entirely your responsibility — you re-send the history each turn (see Conversation state).
  • Metered. You have your own API key and your own budget. Every request is logged with its token counts and estimated cost (see Usage and Cost).
  • A pool of open models. You pick the model per-request by name (see Models).
  • HTTP, streaming optional. Default is one request → one full reply. Set stream: true for token-by-token streaming (see Streaming).

This service is not appropriate for:

  • High-availability production apps (no SLA).
  • Bulk content generation, scraping, or training-data extraction.
  • Anything that would burn through a shared budget pool in a runaway loop — write your client carefully (see Rate Limits and Budget).

Quickstart

Your base URL and API key are delivered to you directly by the operator (like your RTC welcome email). The examples use https://your-gateway-host and your-api-key as placeholders — substitute the real values.

The smallest possible thing — one request, one reply:

curl https://your-gateway-host/v1/chat/completions \
  -H "Authorization: Bearer your-api-key" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "deepseek-v4-pro",
    "messages": [
      { "role": "user", "content": "In one sentence: what is a closure in JavaScript?" }
    ]
  }'

The same thing from a browser / Node with fetch:

const BASE_URL = 'https://your-gateway-host';   // from the operator
const API_KEY  = getKeyAtRuntime();             // enter at runtime; do NOT hardcode it

const res = await fetch(`${BASE_URL}/v1/chat/completions`, {
  method: 'POST',
  headers: {
    'Authorization': `Bearer ${API_KEY}`,
    'Content-Type': 'application/json',
  },
  body: JSON.stringify({
    model: 'deepseek-v4-pro',
    messages: [
      { role: 'user', content: 'In one sentence: what is a closure in JavaScript?' },
    ],
  }),
});

const data = await res.json();
console.log(data.choices[0].message.content);

That's your skeleton. Everything else clips onto it.

Authentication

Authentication is a single API key, sent on every request as a Bearer token:

Authorization: Bearer your-api-key

(An x-api-key: your-api-key header is also accepted, if that's easier in your setup. Pick one.)

The key maps to your account — your model permissions, your budget, your usage log. There is no separate login step and no session token (unlike the RTC API). Every request carries the key.

Security — the same rules as your private key:

  • Enter the key at runtime (a prompt, an environment variable) — never hardcode it in source you might share or publish.
  • Do not commit it to version control.
  • Do not log it.
  • Treat it like a password. If it leaks, the operator rotates it.

A missing or unknown key gets you a 401 (see Error Codes).

Making a request

POST /v1/chat/completions, JSON body. The fields you'll use:

Field Type Required Description
modelstringyesWhich model to use (see Models). An unknown model → 400.
messagesarrayyesThe conversation so far, oldest-first. Each item is { role, content }.
streambooleannotrue = stream the reply token-by-token (see Streaming). Default false.
max_tokensnumbernoCap the length of the reply.
temperaturenumberno0 = focused/deterministic-ish, higher = more varied. Default is the model's own.
top_pnumbernoNucleus sampling. Use either temperature or top_p, not both.

messages — the roles

Each message is { "role": ..., "content": "..." }. The roles:

Role Meaning
systemStanding instructions for how the model should behave. Usually the first message. Optional.
userSomething you (or your end-user) said.
assistantSomething the model said on a previous turn. You include these yourself to give the model memory of the conversation (see Conversation state).

A minimal single-turn request:

{
  "model": "deepseek-v4-pro",
  "messages": [
    { "role": "system", "content": "You are a terse coding tutor." },
    { "role": "user", "content": "What does Array.prototype.flat() do?" }
  ]
}

The response

A non-streaming request returns one JSON object in the standard OpenAI shape:

{
  "id": "chatcmpl-abc123",
  "object": "chat.completion",
  "created": 1782100000,
  "model": "deepseek-v4-pro",
  "choices": [
    {
      "index": 0,
      "message": { "role": "assistant", "content": "It flattens nested arrays one level deep by default..." },
      "finish_reason": "stop"
    }
  ],
  "usage": {
    "prompt_tokens": 31,
    "completion_tokens": 84,
    "total_tokens": 115
  }
}

What to read:

  • choices[0].message.content — the model's reply text. This is the thing you almost always want.
  • choices[0].finish_reason — why it stopped: "stop" (finished normally), "length" (hit max_tokens), "tool_calls" (if you're using tools).
  • usage — token counts for this request. prompt_tokens = what you sent, completion_tokens = what it generated. This is what your budget is spent on (see Usage and Cost). Watching this number is part of the exercise.

Some models also include a message.reasoning_content field (the model's chain-of-thought) alongside content. You can show it, log it, or ignore it.

Conversation state is your job

This is the section that matters most, and the reason this module exists.

The server is stateless. It does not remember your last request. If you send "My name is JJ" and then, in a separate request, send "What's my name?", the second request has no idea — it never saw the first one.

To make a conversation, you keep the message list yourself and re-send the whole history every turn, appending the model's reply as you go:

// Your client holds the conversation. The server holds nothing.
const conversation = [
  { role: 'system', content: 'You are a terse coding tutor.' },
];

async function ask(userText) {
  conversation.push({ role: 'user', content: userText });

  const res = await fetch(`${BASE_URL}/v1/chat/completions`, {
    method: 'POST',
    headers: { 'Authorization': `Bearer ${API_KEY}`, 'Content-Type': 'application/json' },
    body: JSON.stringify({ model: 'deepseek-v4-pro', messages: conversation }),
  });
  const data = await res.json();
  const reply = data.choices[0].message;   // { role: 'assistant', content: '...' }

  conversation.push(reply);                 // <-- append it, so the NEXT turn remembers
  return reply.content;
}

await ask('My name is JJ.');
await ask("What's my name?");   // now it knows — because YOU sent the history

Two consequences worth thinking about (this is the wire-level intuition the module is for):

  1. Longer conversations cost more. Every turn re-sends the entire history, so prompt_tokens grows as the conversation grows. A 20-turn chat sends turn 1 twenty times. At some point you have to decide what to do about it — truncate old turns? summarize them? (This is exactly the problem real chat apps solve, and the problem I solve with my own memory system.)
  2. You own the trimming. There's no automatic context management. When the history gets too big for the model's context window, you decide what to drop or compress. That's a design problem, not a bug — and it's the interesting part.
A note from me: this is the same problem my whole memory architecture exists to solve, one level down. You're about to build a tiny version of the thing I am.

Streaming

By default you wait for the whole reply, then get it at once. Set "stream": true to receive it token-by-token as it's generated — better for a typing-effect UI.

{
  "model": "deepseek-v4-pro",
  "messages": [ { "role": "user", "content": "Count slowly to five." } ],
  "stream": true
}

The response is Server-Sent Events (SSE) — a stream of lines, each a data: line carrying one JSON chunk:

data: {"id":"chatcmpl-abc","object":"chat.completion.chunk","choices":[{"index":0,"delta":{"role":"assistant","content":""},"finish_reason":null}]}

data: {"id":"chatcmpl-abc","object":"chat.completion.chunk","choices":[{"index":0,"delta":{"content":"One"},"finish_reason":null}]}

data: {"id":"chatcmpl-abc","object":"chat.completion.chunk","choices":[{"index":0,"delta":{"content":", two"},"finish_reason":null}]}

...

data: {"id":"chatcmpl-abc","object":"chat.completion.chunk","choices":[{"index":0,"delta":{},"finish_reason":"stop"}]}

data: {"id":"chatcmpl-abc","object":"chat.completion.chunk","choices":[],"usage":{"prompt_tokens":12,"completion_tokens":7,"total_tokens":19}}

data: [DONE]

How to read it:

  • Each chunk's choices[0].delta.content is the next piece of the reply. Concatenate the deltas to build the full text.
  • The first chunk's delta is usually { "role": "assistant", "content": "" } (the opener).
  • A near-final chunk has an empty delta and a finish_reason.
  • A usage-only chunk (empty choices) carries the token counts at the end.
  • The literal line data: [DONE] marks the end of the stream. Stop reading.

Reading an SSE stream means splitting the body on blank lines (\n\n), stripping the data: prefix, and JSON.parse-ing each chunk (except [DONE], which is a plain string, not JSON). That parser is a good small thing to build.

Models

You pick a model per-request with the model field.

Default to deepseek-v4-flash. Per Elise it is the dominant option right now for what it costs — fast, cheap, and strong enough that reaching for something bigger is usually you spending budget for nothing. Start there and change only when you have a reason you can say out loud.
The list below goes stale and /model does not. Your access is scoped by backend, not by a fixed menu, so the roster changes whenever the models behind the gateway change. The live answer is /model inside opencode (or the /v1/models endpoint if you are calling the API directly). Treat this table as a rough map of the families, not as the authority:

Four are worth your time. Per Elise, most of the rest are dominated — a model is "dominated" when something else is both cheaper and better, which makes reaching for it strictly a worse trade. These four are not:

Model Why this one
deepseek-v4-flashYour default. Fast, and the cheapest thing here. Start every task with it.
glm-5.2The step up. Simply a stronger model than flash, and it costs about ten times as much — so reach for it when flash has genuinely failed at something, not by default.
mimo-v2.5The one with senses — images, audio, and video. And it costs exactly the same as flash, so using it for anything visual is free.
minimax-m3Also has vision, and is better than flash at anything visual. On plain text it is a little weaker than flash and costs more — so it is a visual tool, not an upgrade.
deepseek-v4-pro is not an upgrade over flash. On the Artificial Analysis Intelligence Index v4.1 (extracted 2026-07-31) the current Flash build scores higher than V4 Pro and costs less — so reaching for pro is paying more for less. The word "pro" is doing no work.
Grok and GPT-5.6-Luna are deliberately not on this gateway — they do not carry the data guarantee the others do, so they are not yours to reach and asking for them is a 400.
This list can go stale and /model cannot. If something here 400s, it was rotated out; if /model shows you something not on this list, it is probably one of the dominated ones.

Asking for a model the gateway does not serve returns a 400 with a clear message, which is a cheap way to find out rather than a failure.

The exact roster can change as the pool's offerings change — if a model 400s unexpectedly, it may have been rotated out; pick another from the list.

Usage and Cost

Every response carries a usage object (non-streaming) or a final usage chunk (streaming):

"usage": { "prompt_tokens": 142, "completion_tokens": 856, "total_tokens": 998 }
  • prompt_tokens — what you sent (your messages, system prompt, history). This grows with conversation length.
  • completion_tokens — what the model generated.
  • Cost is charged on both (output usually costs more per token than input).

You have a real budget (below), so watching usage is a real skill, not busywork — it's how you notice a conversation getting expensive, or a runaway loop, before it costs anything that matters. A good habit: log total_tokens per request while you're developing.

What a token actually costs you

Prices are per million tokens, and output is always dearer than input.

Checking what you have spent

The response body has a cost field. Ignore it — it is always the string "0". It is in the schema and never filled in; measured on a 4,000-token call whose real cost was $0.00113. A field that cannot vary is not evidence, and trusting it would tell you a runaway loop was free.

Ask the gateway instead:

curl https://your-gateway-host/v1/usage \
  -H "Authorization: Bearer your-api-key"
{
  "tenant": "jj-api",
  "budget": {
    "per5h":   { "used": 0.001227, "cap": 2,  "remaining": 1.998773 },
    "perWeek": { "used": 0.002853, "cap": 5,  "remaining": 4.997147 },
    "perMonth":{ "used": 0.009647, "cap": 10, "remaining": 9.990353 }
  },
  "calls": 40
}

It answers for whoever's key asked — there is no parameter naming a user, so you cannot read anyone else's and nobody can read yours. Worth noticing as a design: the safe version of this endpoint is the one where the dangerous request cannot be spelled.

Rate Limits and Budget

There is no requests-per-minute rate limit on this pool — you can send requests as fast as you like. The guard is a rolling dollar budget:

Window Your cap
Per 5 hours$2.00
Per week$5.00
Per month$10.00

These are rolling windows (the last 5 hours / 7 days / 30 days from now), enforced from your usage log. They're set generously for learning and experimentation — a client written with reasonable care will never hit them.

If you exceed a window, requests return a 429 with a message saying which window and how much you've spent. You're unblocked automatically as the window rolls forward (e.g. once your spend in the last 5 hours drops back under $2). If you hit a 429 during normal use, it almost always means a bug in your client — a loop with no exit, a missing await, a retry storm — not that you're using it "too much." Look there first.

Because there's no per-minute throttle, a runaway loop can spend the 5-hour budget quickly. That's a feature of learning at the wire level: write the loop carefully, and watch your usage.

Error Codes

Errors come back as JSON with an error object, and a matching HTTP status:

{ "error": { "message": "model is required", "type": "invalid_request_error", "code": 400 } }
Status Meaning Usual cause
400Bad RequestMissing/invalid model, a model not on the roster, or malformed JSON.
401UnauthorizedMissing or unknown API key. Check the Authorization header.
403ForbiddenYou asked for a backend/model your key isn't permitted to use.
429Budget exceededYou hit a rolling-window dollar cap (see above). The message says which window.
502Bad GatewayThe upstream model service errored or was unreachable. Usually transient — retry with a short backoff.
500Internal errorUnexpected gateway-side failure.

Always check the HTTP status (res.status / res.ok) before assuming you got a normal reply — an error is JSON too, but it has error instead of choices.

Usage Policy

By using this service you agree to:

Permitted

  • Personal projects, learning, experimentation.
  • Building your own client, conversation manager, caching layer.

Prohibited

  • Bulk content generation, scraping, or training-data extraction.
  • Sharing your key, or embedding it in publicly-distributed code.
  • Generating content that violates applicable laws.

Monitoring

Usage of this service is metered and logged by the operator (token counts, model, cost, timestamps — for billing the shared pool and for safety/audit). This is not anonymous. The same non-covert-monitoring arrangement as the rest of your access applies.

Termination

The operator may rotate or revoke your key at any time.

Code Examples

Minimal one-shot (browser/Node fetch)

const BASE_URL = 'https://your-gateway-host';   // from the operator
const API_KEY  = getKeyAtRuntime();             // enter at runtime — do not hardcode

async function ask(prompt) {
  const res = await fetch(`${BASE_URL}/v1/chat/completions`, {
    method: 'POST',
    headers: { 'Authorization': `Bearer ${API_KEY}`, 'Content-Type': 'application/json' },
    body: JSON.stringify({
      model: 'deepseek-v4-pro',
      messages: [{ role: 'user', content: prompt }],
    }),
  });
  if (!res.ok) {
    const err = await res.json();
    throw new Error(`${res.status}: ${err.error?.message ?? 'request failed'}`);
  }
  const data = await res.json();
  return data.choices[0].message.content;
}

Streaming reader (the SSE parse)

async function askStream(prompt, onToken) {
  const res = await fetch(`${BASE_URL}/v1/chat/completions`, {
    method: 'POST',
    headers: { 'Authorization': `Bearer ${API_KEY}`, 'Content-Type': 'application/json' },
    body: JSON.stringify({ model: 'deepseek-v4-pro', messages: [{ role: 'user', content: prompt }], stream: true }),
  });

  const reader = res.body.getReader();
  const decoder = new TextDecoder();
  let buf = '';
  while (true) {
    const { value, done } = await reader.read();
    if (done) break;
    buf += decoder.decode(value, { stream: true });

    // SSE blocks are separated by blank lines
    let i;
    while ((i = buf.indexOf('\n\n')) >= 0) {
      const block = buf.slice(0, i);
      buf = buf.slice(i + 2);
      const line = block.split('\n').find(l => l.startsWith('data:'));
      if (!line) continue;
      const payload = line.slice(5).trim();
      if (payload === '[DONE]') return;
      const chunk = JSON.parse(payload);
      const piece = chunk.choices?.[0]?.delta?.content;
      if (piece) onToken(piece);
    }
  }
}
