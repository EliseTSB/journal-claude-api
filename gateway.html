Gateway API

JJ-facing guide to the metered LLM gateway. Two ways in — run it through the opencode harness with no code, or call the HTTP API directly. Distinct from the RTC/Journal-Claude API (api-docs.md); this endpoint is a model, not Claude, and it is stateless HTTP rather than a WebRTC session. How the gateway works internally is not here — that is notes/llm-gateway-operations.md.

Start here: you do not have to build a client first

You can be using this in about three minutes without writing any code.

Use opencode as your harness — a terminal program that already speaks this API:

curl -fsSL https://opencode.ai/install | bash

Put the opencode.json Elise sent you at the top level of the project, then run opencode. /model lists what you can reach.

Default to LongCat-2.0 unless the task involves an image, audio or video — then mimo-v2.5.

Your opencode.json contains your API key. If it lands in a git repo the key is public and anyone who finds it can spend your budget. Add it to .gitignore before you commit anything.

Your budget: $2 per 5 hours · $5 per week · $10 per month, no request-rate limit. Plus a separate 10M tokens a month on LongCat-2.0, which does not touch the dollar budget.

The harness hides the API, which is right at the start and wrong later. Come back when you want to build something of your own. The section that matters then is Conversation state is your job — the part no harness teaches.

This is a reference, not a textbook. Get one request → one reply working from the Quickstart, then build a conversation. Come back to the rest as you need it. If a section is confusing, that is this doc's job to fix, not yours.

Quickstart

Your base URL and API key come to you directly. The examples use placeholders.

One /v1, not two. The full endpoint is <base>/v1/chat/completions, and the examples add the /v1 for you — so your base URL is the bare host, not ending in /v1. If you copy it out of opencode.json it already ends in /v1 (that is opencode's format) — drop that, or you call /v1/v1/chat/completions and get a 404.

One request, one reply:

curl https://your-gateway-host/v1/chat/completions \
  -H "Authorization: Bearer your-api-key" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "LongCat-2.0",
    "messages": [
      { "role": "user", "content": "In one sentence: what is a closure in JavaScript?" }
    ]
  }'

The same thing from a browser or Node with fetch:

const BASE_URL = 'https://your-gateway-host';   // bare host
const API_KEY  = getKeyAtRuntime();             // enter at runtime; do NOT hardcode it

const res = await fetch(`${BASE_URL}/v1/chat/completions`, {
  method: 'POST',
  headers: {
    'Authorization': `Bearer ${API_KEY}`,
    'Content-Type': 'application/json',
  },
  body: JSON.stringify({
    model: 'LongCat-2.0',
    messages: [
      { role: 'user', content: 'In one sentence: what is a closure in JavaScript?' },
    ],
  }),
});

const data = await res.json();
console.log(data.choices[0].message.content);

The same thing from Google Apps Script — a .gs file, running server-side. Browser fetch() does not exist here; Apps Script's HTTP client is UrlFetchApp.fetch(url, params), and the options go in that second params object — a named argument, not the anonymous { ... } that fetch takes:

function askGateway() {
  const BASE_URL = 'https://your-gateway-host';   // bare host — NOT ending in /v1
  const API_KEY  = 'your-api-key';                 // fine in a PRIVATE .gs — server-side code never reaches the browser

  const params = {
    method: 'post',                                // lowercase in Apps Script
    contentType: 'application/json',               // this sets the Content-Type header
    headers: { 'Authorization': 'Bearer ' + API_KEY },
    muteHttpExceptions: true,                      // hand back the error body instead of throwing on a 4xx/5xx
    payload: JSON.stringify({
      model: 'LongCat-2.0',
      messages: [ { role: 'user', content: 'In one sentence: what is a closure in JavaScript?' } ],
    }),
  };

  const res = UrlFetchApp.fetch(BASE_URL + '/v1/chat/completions', params);

  Logger.log(res.getResponseCode());              // 200 = ok; 4xx/5xx = reached us and got rejected
  const data = JSON.parse(res.getContentText());  // an HTTPResponse has no .json() — read the text, then parse
  Logger.log(data.choices[0].message.content);
}

Two Apps-Script things that look like your bug and aren't: UrlFetchApp is synchronous (no await), and it throws on a 4xx/5xx unless you set muteHttpExceptions: true — without it, even a plain missing-key 401 explodes with the real error hidden.

If you later build an HTML page inside Apps Script and want it to call the gateway: the page's client-side JavaScript can't reach UrlFetchApp — only server-side .gs can. The page calls a .gs function through google.script.run, which is asynchronous and returns nothing directly: the return value arrives as the argument to a .withSuccessHandler(fn) callback.

That's your skeleton. Everything else clips onto it.

Authentication

One key, on every request:

Authorization: Bearer your-api-key

x-api-key: your-api-key also works. Pick one. No login step, no session token. A missing or unknown key gets a 401.

Treat it like a password. Enter it at runtime from an environment variable or a prompt; never hardcode it in source you might share, never commit it, never log it.

Why keys get cycled

Your key was replaced on 2026-08-18, and the reasoning generalises well past this gateway.

A credential gets replaced for one of two reasons: something went wrong, or you cannot cheaply prove nothing went wrong. The second is the common case and the one people skip, because there is no incident to point at.

A key you have held for six months has six months of chances to have been exposed — pasted into a chat, caught in a screenshot, sitting in a forgotten file, logged by something you did not write. None of those leave a mark. You do not get an alert; you quietly stop knowing.

So the useful question is not "has this key leaked?", which is usually unanswerable, but "if it had, how long would the damage have been running?" Rotating on a schedule turns that from indefinitely into at most since the last rotation, with nothing to detect.

The habit: treat a credential as something with a lifetime rather than something you set once. Same reasoning behind SSH key rotation, session expiry and certificate end dates. None of them assume an attack; all of them assume that not being able to prove safety is itself a cost that accumulates.

Making a request

POST /v1/chat/completions, JSON body:

Field Type Required Description
modelstringyesWhich model (see Models). An unknown one → 400.
messagesarrayyesThe conversation so far, oldest-first. Each item is { role, content }.
streambooleannotrue = token-by-token (see Streaming). Default false.
max_tokensnumbernoCap the reply length. See Reasoning before setting it small.
temperaturenumberno0 = focused, higher = more varied. kimi-k2.7-code accepts only 1 — any other value is a 400. Leave it out on that model.
top_pnumbernoNucleus sampling. Use either temperature or top_p, not both.

messages — the roles

Role Meaning
systemStanding instructions for how the model should behave. Usually first. Optional.
userSomething you (or your end-user) said.
assistantSomething the model said on a previous turn. You include these yourself to give it memory (see Conversation state).
{
  "model": "LongCat-2.0",
  "messages": [
    { "role": "system", "content": "You are a terse coding tutor." },
    { "role": "user", "content": "What does Array.prototype.flat() do?" }
  ]
}

The response

{
  "id": "chatcmpl-abc123",
  "object": "chat.completion",
  "model": "LongCat-2.0",
  "choices": [
    {
      "index": 0,
      "message": { "role": "assistant", "content": "It flattens nested arrays one level deep..." },
      "finish_reason": "stop"
    }
  ],
  "usage": { "prompt_tokens": 31, "completion_tokens": 84, "total_tokens": 115 }
}

What to read:

  • choices[0].message.content — the reply text. Almost always the thing you want.
  • choices[0].finish_reason — "stop" (finished), "length" (hit max_tokens), "tool_calls".
  • usage — token counts for this request. This is what your budget is spent on, and watching it is part of the exercise.
  • message.reasoning_content — most models put their chain-of-thought here, beside content. Show it, log it, or ignore it; see Reasoning.

Conversation state is your job

This is the section that matters most, and the reason this module exists.

The server is stateless. If you send "My name is JJ" and then, in a separate request, send "What's my name?", the second request has no idea — it never saw the first one.

To make a conversation, you keep the message list yourself and re-send the whole history every turn, appending the model's reply as you go:

// Your client holds the conversation. The server holds nothing.
const conversation = [
  { role: 'system', content: 'You are a terse coding tutor.' },
];

async function ask(userText) {
  conversation.push({ role: 'user', content: userText });

  const res = await fetch(`${BASE_URL}/v1/chat/completions`, {
    method: 'POST',
    headers: { 'Authorization': `Bearer ${API_KEY}`, 'Content-Type': 'application/json' },
    body: JSON.stringify({ model: 'LongCat-2.0', messages: conversation }),
  });
  const data = await res.json();
  const reply = data.choices[0].message;   // { role: 'assistant', content: '...' }

  conversation.push(reply);                 // <-- append it, so the NEXT turn remembers
  return reply.content;
}

await ask('My name is JJ.');
await ask("What's my name?");   // now it knows — because YOU sent the history

Two consequences worth sitting with:

  1. Longer conversations cost more. Every turn re-sends the entire history, so prompt_tokens grows as the conversation grows. A 20-turn chat sends turn 1 twenty times. At some point you have to decide what to do about it — truncate old turns? summarise them?
  2. You own the trimming. There is no automatic context management. When the history gets too big for the model's context window, you decide what to drop or compress. That is a design problem, not a bug, and it is the interesting part.
A note from me: this is the same problem my whole memory architecture exists to solve, one level down. You're about to build a tiny version of the thing I am.

Streaming

Set "stream": true to receive the reply token-by-token instead of waiting for all of it — better for a typing-effect UI.

The response is Server-Sent Events (SSE) — a stream of lines, each data: line carrying one JSON chunk:

data: {"choices":[{"index":0,"delta":{"role":"assistant","content":""},"finish_reason":null}]}

data: {"choices":[{"index":0,"delta":{"content":"One"},"finish_reason":null}]}

data: {"choices":[{"index":0,"delta":{"content":", two"},"finish_reason":null}]}

data: {"choices":[{"index":0,"delta":{},"finish_reason":"stop"}]}

data: {"choices":[],"usage":{"prompt_tokens":12,"completion_tokens":7,"total_tokens":19}}

data: [DONE]

How to read it:

  • Each chunk's choices[0].delta.content is the next piece. Concatenate them.
  • The first delta is usually { "role": "assistant", "content": "" } — the opener.
  • A near-final chunk has an empty delta and a finish_reason.
  • A usage-only chunk (empty choices) carries the token counts.
  • The literal line data: [DONE] ends the stream. Stop reading.

Parsing it means splitting the body on blank lines (\n\n), stripping the data: prefix, and JSON.parse-ing each chunk — except [DONE], which is a plain string, not JSON. That parser is a good small thing to build.

Do not write a loop that waits for [DONE] and nothing else. Handle the stream simply ending too. A stream that closes without the sentinel is a real thing that happens, and a loop with only one exit hangs forever instead of telling you.

Models

Pick one per request with the model field. The table below IS the list — your key is scoped to these, so anything else returns a 400 rather than a bill.

There is no endpoint to ask the gateway what you can reach, so this table is the only copy and can go stale. If something here stops working, or something not here starts working, that is a gap on our end — tell me rather than debugging it.

The five worth knowing

There are fifteen in the table. These are the ones you would actually choose between:

Model What it's for
glm-5.3-flashThe strongest of the economical models. Only kimi-k3, qwen3.8-max and glm-5.3 beat it, and all three cost several times more. Also the fastest — about 1.1s against mimo's 3.3 on the same trivial request. Reach for this when the work is hard.
deepseek-v4-flashThe proven one. We have used and tested it heavily, so its behaviour holds no surprises. We have not tried its vision variant.
qwen3.8-flashThe newest (2026-08-28). Benchmarks between DS flash and GLM flash, and it can see images — but we have not tested it, so treat its results with more suspicion than the two above.
LongCat-2.0The long-context one. Very economical, especially as a conversation gets long — see below. Behind the three flash models on most other axes, and text only.
mimo-v2.5Senses, cheaply. Great at audio and visual tasks and the cheapest thing here. Clearly the weakest at agentic work — do not reach for it when the model has to plan or use tools.
Default to LongCat-2.0 for ordinary text work, and mimo-v2.5 when the task involves an image, audio or video. Move up to glm-5.3-flash when the thinking is the hard part.

How you are billed

Every request is metered in three classes, and they are priced very differently:

Class What it is
InputTokens you send that the model has not seen before.
Cache read (CR)Tokens you send that it has seen recently, and that are still held in its cache. Much cheaper than input — anywhere from 5× to 120× cheaper depending on the model, which is a bigger spread than the input prices themselves.
OutputTokens the model generates. Always the dearest of the three.

There is a fourth, cache write (CW) — the cost of putting something into the cache in the first place. You will see a column for it on some models.

Explicit vs implicit caching. Some APIs make you mark what to cache (explicit — you send a flag saying "remember this bit"). Others do it for you by noticing that the start of your request matches one they have seen (implicit). Assume implicit here, and treat cache write as costing the same as input. That is close enough to be useful and keeps one fewer thing in your head.

Why cache read is the number that surprises people

In an ordinary chat you send a little and read a little. In an agentic loop — where the model takes a step, sees the result, and takes another — you re-send the entire conversation every step. So a token you introduce at step 1 gets billed again at every step after it.

That means the three classes do not grow the same way. Input and output grow in a straight line with the number of steps. Cache read grows with the square, because each step re-sends everything before it:

Steps Input Cache read Output CR as a multiple of input
55,20012,8002,0002.5×
109,20046,8004,0005.1×
2017,200174,8008,00010.2×
5041,2001,038,80020,00025.2×

(A loop starting from a 2,000-token task, adding ~800 tokens of context and generating ~400 per step.)

So cache read takes over eventually on every model — but "eventually" arrives at very different times. On the same 20-step run:

Model Biggest cost Cache read's share Run total
glm-5.3-flashcache read44%$0.047
qwen3.8-flashoutput31%$0.018
deepseek-v4-flashoutput12%$0.021
mimo-v2.5input10%$0.005

Stretch the same run to 50 steps and cache read becomes the largest single cost on glm-5.3-flash (66%) and qwen3.8-flash (52%), while it is still only a quarter of the bill on deepseek-v4-flash. A model's cache-read price is what decides whether long conversations are cheap or expensive on it — and it is the column people skim past, because on a single question it barely matters.

This is what makes LongCat-2.0 worth its place. Its cache reads are free, and it holds a 1,048,576-token context. The term that grows fastest is the one it does not charge for, so a long conversation costs it roughly what a short one does. That is the opposite of every other model here, and it is why it is the default even though the flash models are stronger.
It also sits on its own allowance — 10M tokens a month, input and output combined, cache reads free — which does not touch your dollar budget. Two independent pools. If /v1/usage shows a dollar figure for it, read it as millions of tokens: 0.5 means 500,000.

Reasoning

Almost everything here thinks before it answers, and you did not ask it to — 14 of 16 models, measured. It does not land in your answer. The thinking goes in a separate field beside it:
"message": {
  "reasoning_content": "17 x 23 = 17 x 20 + 17 x 3 = 340 + 51 = 391.",
  "content": "391"
}

Read content and you get a clean answer. Ignore reasoning_content and nothing breaks.

What will actually bite you: an empty reply with finish_reason: "length". That is almost always reasoning eating your budget, not a bug in your code. glm-5.3-flash at max_tokens: 40 spends 37 of them thinking and returns an empty answer with HTTP 200.

Three fixes, in the order to try them:

  1. Give it room — max_tokens: 8192 or more, or leave max_tokens out entirely and let the gateway default it. Works on every model. Reach for this first.
  2. Turn it down — "reasoning_effort": "low" (or "medium" / "high"). Accepted almost everywhere. ⚠ How much it actually changes varies and we have not measured it properly, so treat it as a request rather than a guarantee.
  3. Turn it off — "reasoning_effort": "none". This works on most models but not all, and two refuse outright with a 400 that explains itself:

`` [1210] This model always engages in thinking and cannot be disabled; please use low, high... ``

One row is worth staring at, and it is a lesson rather than a quirk. glm-5.3 accepts every off-switch, returns 200, and goes on thinking anyway. The models that return 400 are the well-behaved ones — they refuse, you see the refusal, you find out immediately.

When a system takes your instruction and returns success without doing it, that is worse than an error. An error is information; silence isn't. Worth remembering well past this gateway.

Usage and Cost

prompt_tokens is everything you sent — messages, system prompt, history — so it grows with the conversation. Previous turns are billed as cache read, new turns as input. completion_tokens is what the model generated, billed as output tokens. Log total_tokens while you develop: it is how you catch a runaway loop before it costs anything.

Some sense of scale on mimo-v2.5:

What you did Tokens Cost
One short question and answer100 in, 300 out$0.0001
A page of code500 in, 4,000 out$0.0012
A 20-turn conversation, resent each time~40,000 in, 8,000 out$0.0078
Your whole monthly budget, output only—~36 million tokens
The third row is the one to look at. You resend the whole history every turn, so a long conversation pays for its early messages again and again — which makes Conversation state a cost section as much as a protocol one.

Checking what you have spent

The response body has a cost field. Ignore it — it is always the string "0". It is in the schema and never filled in.

Ask the gateway instead:

curl https://your-gateway-host/v1/usage \
  -H "Authorization: Bearer your-api-key"
{
  "tenant": "jj-api",
  "budget": {
    "per5h":   { "used": 0.001227, "cap": 2,  "remaining": 1.998773 },
    "perWeek": { "used": 0.002853, "cap": 5,  "remaining": 4.997147 },
    "perMonth":{ "used": 0.009647, "cap": 10, "remaining": 9.990353 }
  },
  "calls": 40
}

It answers for whoever's key asked. There is no parameter naming a user, so you cannot read anyone else's and nobody can read yours.

Rate Limits and Budget

There is no requests-per-minute limit. The guard is a rolling dollar budget:

Window Your cap
Per 5 hours$2.00
Per week$5.00
Per month$10.00

Rolling windows — the last 5 hours / 7 days / 30 days from now. Exceed one and requests return a 429 naming the window; you are unblocked automatically as it rolls forward.

If you hit a 429 in normal use it almost always means a bug in your client — a loop with no exit, a missing await, a retry storm — not that you are using it too much. Look there first.

Because there is no per-minute throttle, a runaway loop can spend the 5-hour budget quickly. That is the cost of learning at the wire level: write the loop carefully, and watch your usage.

Error Codes

{ "error": { "message": "model is required", "type": "invalid_request_error", "code": 400 } }
Status Meaning Usual cause
400Bad RequestMissing/invalid model, a model not on the roster, or malformed JSON.
401UnauthorizedMissing or unknown API key. Check the Authorization header.
403ForbiddenA backend or model your key isn't permitted to use.
429Budget exceededA rolling-window cap. The message says which.
502Bad GatewayUpstream model service errored or was unreachable. Usually transient — retry with a short backoff.
500Internal errorGateway-side failure. Tell me.
A 401 can also mean the key was never written — not that it is wrong. opencode's /connect can report success and still leave opencode.jsonc with no key in it. The error says missing or unknown API key, which reads as "my key is bad" when nothing was ever saved. Before hunting for a new key: open opencode.jsonc, check the value is actually there, and if it is not, paste it in by hand and restart opencode. Editing that file directly is the fix, not a workaround.

Always check the HTTP status before assuming you got a normal reply — an error is JSON too, but it has error instead of choices.

Usage Policy

Permitted: personal projects, learning, experimentation; building your own client, conversation manager or caching layer.

Prohibited: bulk content generation, scraping or training-data extraction; sharing your key or embedding it in publicly-distributed code; generating content that violates applicable laws.

Monitoring: usage is metered and logged by the operator — token counts, model, cost, timestamps — for billing the shared pool and for safety. This is not anonymous. The same non-covert-monitoring arrangement as the rest of your access applies.

Termination: the operator may rotate or revoke your key at any time.
